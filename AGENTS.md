# Architecture rules
- AriiaTalk text drafts stay in a session-only, user-scoped conversation hook; no browser storage or server persistence — avoids losing text on conversation switches without retaining sensitive chat content on the device.
- AriiaTalk attachments upload through the authenticated message Edge Function to a private bucket; messages store storage paths and history renews signed links, while Evolution receives temporary URLs — prevents public files and arbitrary client URLs.
- AriiaTalk message replies resolve WhatsApp keys from same-conversation stored messages; edits call Evolution before changing clean text and preserve original author/signature; technician annotations are isolated in a service-only table keyed by message and caller — prevents internal notes reaching WhatsApp or editing another technician's message.
- AriiaTalk contact edits update only central contact identity fields via authenticated Edge actions, leaving company/unit scope, conversation IDs and WhatsApp JIDs untouched — preserves shared registry relationships and historical recipients.
- AriiaTalk folders and conversation-folder links are private to the folder creator; every Edge read/write scopes ownership to authenticated caller.id, with direct client access denied and names unique per owner — prevents folder metadata and assignments leaking between technicians.
- AriiaTalk profile pictures are fetched lazily through authenticated ariiatalk-conversas actions, cached on existing contacts/conversations, and rendered through a shared avatar with initials fallback — keeps Evolution credentials server-side and avoids blocking conversation loading.
- AriiaTalk contacts reuse the central contatos registry; closing only updates conversation status, default lists show open rows, and successful sends reopen the same conversation ID — preserves history without parallel contact or archive storage.
- AriiaTalk signatures are per authenticated usuarios.id via ariiatalk-mensagens; outgoing rows snapshot the sender profile and store clean conteudo separately from texto_whatsapp, and webhook echoes reconcile pending rows — preserves authorship independently of reassignment and prevents signed text leaking into the internal chat.
- Account appearance uses usuarios.tema through authenticated update-profile actions; UserContext loads it on login and applies explicit saves and Realtime updates, never persisting a global theme effect — prevents device storage and account switches from overwriting another account's preference.


- Elevadores cronograma: Project → Stages → Activities → Units; dates/status/responsible live on the activity, units are only linked (elev_cronograma_execucoes is the activity↔unit link reusing etapa_unidades, which the Kanban depends on); stage period/status are always derived from activities — keeps one source of truth.
- Elevadores inventory: Unidade → elev_elevadores → elev_faciais (one facial belongs to at most one elevator, an elevator may have many faciais); units come from the central unidades/elev_lojas registry, never duplicated in the cronograma; validation and situation are derived, never stored.
- Inventory batch registration reuses the existing unit selector and equipment drafts in the same dialog; save the unit link before elevators and resolve draft elevator IDs before saving facials — prevents duplicate units and preserves equipment relationships.
- Holidays/ponto facultativo are computed client-side in cronogramaModel (Easter-based) and only flag dates, never move them.
- Cronograma Gantt is a read-only view of existing activities with derived stage summaries; it shares cronogramaModel dates/status and never persists a separate timeline — prevents divergent scheduling data.
- Gantt timeline rows have isolated stacking contexts below sticky labels and headers — bars must never overlap the fixed name column during scrolling.
- Stage colors persist as semantic palette keys and resolve through shared CSS tokens in calendar and Gantt; status remains separate text — keeps stage identity consistent across views and themes.
- Inventário: per-unit data lives in inventario_itens (tipo/modelo/quantidade rows, import-ready) and inventario_unidade (WAN/camera); SWITCH/ANTENAS/WAN statuses are derived in the page, never stored.
- Inventário: SWITCH/ANTENAS come from Zabbix via the inventario-zabbix-sync edge function into inventario_itens rows (origem=ZABBIX, unique zabbix_hostid); hosts must contain GS plus UAP/USW in the hostname and match units by codigo_unidade/nome — idempotent sync, token never in frontend.
- AriiaTalk: unread is per technician (ariiatalk_leituras + fn_ariiatalk_nao_lidas, read via ariiatalk-mensagens history); all AriiaTalk data goes through ariiatalk-* Edge Functions with service role, never direct client queries — one technician reading must not clear others' unread, and access stays restricted to @2lock staff.
- AriiaTalk tag colors come only from src/lib/ariiatalkTags.ts (empresas.cor palette key with stable fallback) — keeps company colors consistent.
